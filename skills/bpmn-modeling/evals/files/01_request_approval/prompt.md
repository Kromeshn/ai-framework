# Согласовать заявку с возвратом на исправление

Построить локальную описательную BPMN-схему по приведённому порядку. Все названия и сведения синтетические. Обычные действия показать как task без маркера исполнителя. Имена действий сохранить полностью. Не добавлять окончательный отказ, отмену или третий исход согласования.

Граница процесса: от возникновения потребности в учебном изменении до согласования заявки и сохранения протокола. Один экземпляр — одна заявка. Три дорожки в одном пуле: «Заявитель», «Координатор», «Согласующий». Документы разместить над связанными действиями; отдельную четвёртую дорожку в этом кейсе не добавлять.

1. На дорожке заявителя простой старт «Возникла потребность в учебном изменении» ведёт к действию «Подготовить заявку с описанием цели, ожидаемого результата и необходимыми приложениями». Действие создаёт документ «Заявка на учебное изменение с обоснованием и необходимыми приложениями».
2. На дорожке координатора действие «Проверить полноту сведений и соответствие приложений заявленному результату» читает заявку. Первый запуск и возврат после исправления соединяются перед этой проверкой через сходящийся исключающий шлюз.
3. Исключающий шлюз «Сведения и приложения полны?» имеет ровно две ветки. «Да» (complete = true) ведёт к согласующему. «Нет» (complete = false) ведёт к исправлению. Поле complete — определённое логическое значение, которое устанавливается проверкой.
4. Согласующий выполняет «Оценить обоснованность учебного изменения и возможность достижения заявленного результата», читая заявку. Далее исключающий шлюз «Заявка согласована?». «Да» (approved = true) ведёт к регистрации протокола. «Нет» (approved = false) ведёт к исправлению. Поле approved устанавливается оценкой; неопределённого значения нет.
5. Обе причины исправления объединяются через сходящийся исключающий шлюз «Получены замечания к заявке?» на дорожке согласующего; этот шлюз ничего не ожидает и не означает дополнительного решения. Заявитель выполняет «Исправить заявку и приложения по замечаниям координатора или согласующего». Читается и обновляется тот же документ заявки. Переход всегда возвращает к проверке полноты, включая повтор согласования после успешной проверки. Число повторов не ограничивается.
6. При согласовании координатор выполняет «Зафиксировать согласование и сохранить протокол с итоговыми условиями выполнения», создавая документ «Протокол согласования заявки с итоговыми условиями выполнения». Затем простой конец «Заявка согласована, протокол сохранён».

Создание и обновление документов показать dataOutputAssociation, чтение — dataInputAssociation через корректные входы/выходы ioSpecification. Документы не являются задачами и не получают sequenceFlow. Данные задачи описательные; готовность к исполнению в движке не требуется.
