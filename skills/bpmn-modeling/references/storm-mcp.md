# Работа со StormBPMN через MCP

Ресурс применяется только при моделировании в StormBPMN. Согласованный смысл процесса остаётся основой; правила платформы не подменяют бизнес-требования.

## Подключение и возможности

Использовать уже подключённый MCP StormBPMN. Ключи, пользовательские пути и идентификаторы демонстрационных диаграмм в навык не включаются. Навык не устанавливает сервер и не меняет конфигурацию без соответствующего запроса.

До использования операции проверить текущую схему инструмента. Для пакетных правок получить параметры нужных операций через `describe_edit_operation`. Не фиксировать число инструментов и ограничения API навсегда.

Чтение метаданных элемента не означает, что MCP умеет создавать такой же элемент: отдельно проверять операции создания и изменения. Документ в справочнике активов и значок объекта данных на BPMN-полотне — разные сущности. Не подменять одно другим. Если операция недоступна через MCP, описать точное ограничение и продолжать доступную часть задачи; другой редактор использовать в соответствии с выбором пользователя.

Публичные сведения: [Storm MCP](https://stormbpmn.com/mcp). Текущие описания инструментов и ответы сервера определяют техническую доступность функции. При противоречивой справке проверить нужную операцию безопасным предпросмотром либо на отдельно разрешённом тестовом объекте; не экспериментировать записью в рабочую схему.

## Новая модель

1. Для целой схемы рассмотреть `create_diagram_from_sketch`: Mermaid служит входным наброском, результатом должна быть BPMN-модель. Для пошаговой сборки использовать `create_diagram` и `edit_diagram`.
2. Брать возвращённый `diagramId`, идентификаторы узлов и точные названия из ответа или `get_diagram_flow`. Идентификаторы исходного Mermaid-наброска после создания не сохраняются.
3. Группировать связанные изменения в пакет. Сложные операции сначала проверить через `dryRun`, если поддерживается; затем сохранить.
4. После структурных правок новой схемы выполнить `relayout_diagram`, если требуется раскладка.
5. Повторно прочитать сохранённую модель и проверить сценарии. Использовать возвращённый сервером URL результата.

## Существующая модель

Читать через `get_diagram_flow` и при необходимости `get_element_details`. Перед визуальными правками читать `get_diagram_geometry`.

`relayout_diagram` заменяет ручное расположение: после небольшой правки не запускать автоматически. Для локального перемещения применять `set_diagram_geometry`. При перемещении узла обновлять маршруты всех затронутых стрелок: автоматическая перепривязка не гарантируется. Проверять предупреждения и визуальный результат.

Дорожки создаются через `add_lane` и `assign_to_lane`; роли назначаются отдельно через `set_assignee` или `set_assignees`. Не создавать записи справочников только из-за появления дорожки. Перед созданием роли или актива искать существующие варианты и переиспользовать подходящий.

При пакетном обогащении проверять каждый результат: общий `success=true` может означать частичный успех. Повторять только исправленные неуспешные элементы. После потери ответа на создание сначала проверить наличие объекта, чтобы не создать дубликат.

## Проверка и границы применения

Проверять смысл маршрутов, результат линтера и читаемость отдельно. Рутинные исправления ограничить двумя-тремя проходами; если проблема сохраняется, точно описать ограничение и сохранить пригодный результат без бесконечных попыток.

Поддержка дорожек, подпроцессов, событий, нескольких пулов и сообщений зависит от текущего API. Различать «недоступно в MCP», «доступно в редакторе» и «недопустимо в BPMN». Не заменять поток сообщений потоком управления через границы пулов.

Симуляции, создание справочников, публикация wiki и рассылки не являются обязательными этапами рисования. Выполнять их только в рамках пользовательской задачи. Обозначенный на схеме шаг отправки письма не означает отправку реального сообщения.

Восстановление версии может заменить более свежие изменения; оно применяется только по соответствующему поручению.
